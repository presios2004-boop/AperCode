# AperCode

[English](README.en.md)

ローカル LLM（Ollama）で動く汎用コーディングエージェント。Web ブラウザ UI 付き。
MT5 (wine) の EA コンパイル・バックテストをツールとして組み込み済み。
コンテキスト自動圧縮とサブエージェント（子エージェント）に対応し、中規模プロジェクトの構築を想定。

```
├── main.py                 # サーバーのみ起動

├── LICENSE                 # MIT
├── config.yaml             # 設定（モデル・権限・MT5 パス）
├── codeagent/
│   ├── agent.py            # エージェントループ（LLM ⇄ ツール）
│   ├── llm.py              # Ollama / Anthropic クライアント
│   ├── prompts.py          # システムプロンプト
│   ├── session.py          # 会話履歴の保存（JSON）
│   ├── memory/store.py     # 経験メモリ（SQLite FTS5 + 埋め込みベクトル）

│   │   ├── subagent.py     # spawn_agent（子エージェント）
│   │   ├── web.py          # web_search / fetch_url
│   │   ├── backup_tools.py # list_backups / restore_backup
│   │   └── icon.py         # make_icon（アイコン生成、CLI 兼用）
│   ├── backup.py           # 変更前ファイルの自動バックアップ
│   │   ├── memory_tools.py # search_memory / save_memory

│       └── static/index.html
```

## セットアップ

### インストールの順番（Linux。zip を展開した場合）

同梱のスクリプトは 2 つ。役割が違うので、次の順番で実行する（どちらも AperCode のフォルダで実行）。

| 順番 | スクリプト | 何をするか | 必要か |
|---|---|---|---|
| 1 | `setup_linux_window.sh` | apt で GTK / WebKit2GTK（日本語入力が使える専用ウィンドウ用）を入れ、AperCode 用の仮想環境 `.venv` を作って `requirements.txt` を入れる | 推奨（sudo のパスワードを聞かれる） |
| 2 | `install_desktop.sh` | アプリメニュー（開発）とデスクトップに「AperCode」を登録するだけ。`.venv` が必要なので 1 の後に実行する | 任意（メニューから起動したいとき） |

```bash
cd AperCode                       # zip を展開したフォルダ
bash setup_linux_window.sh        # 1. 依存パッケージと .venv
bash install_desktop.sh           # 2. メニュー・デスクトップに登録
sudo apt install bubblewrap       # 推奨: コマンドのサンドボックス（v2.5.0）
ollama pull qwen3:8b bge-m3       # 使うモデルと埋め込みモデル
```

- 1 を使わない場合（apt を使いたくない・日本語入力が不要）は、代わりに手動で `.venv` を作る:
  `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`。そのあと 2 を実行する
- `setup_linux_window.sh` は実行するたびに `.venv` を作り直す。あとから実行しても、2 をやり直す必要はない
- Windows / macOS ではスクリプトは使えない。下の手順で手動でセットアップし、`python3 app.py` で起動する
- 初回起動時、画面上部に「作業ディレクトリがありません」と出たら「作成する」を押す（AperCode が作業するフォルダ
  `~/Documents/Aper_work` と、その中の `.venv` を作る）
- `.venv` は 2 種類ある。AperCode のフォルダの `.venv` は **AperCode 自身を動かす**ためのもの、作業ディレクトリの `.venv` は
  **AperCode が作るコードを動かす**ためのもの。AperCode が `pip install` するのは作業ディレクトリの方

### 手動でセットアップする場合

```bash
cd codeagent
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m playwright install chromium  # 任意: ブラウザ機能（v1.4.0）用の Chromium
cp config.example.yaml config.yaml     # 任意。無ければ config.example.yaml がそのまま使われる
ollama pull qwen3:8b bge-m3            # 使うモデルと埋め込みモデル
```

設定は 3 段階で読み込まれる（後のものが優先）:
1. `config.example.yaml`（リポジトリ同梱の既定値）
2. `config.yaml`（プロジェクト直下。`.gitignore` 済み）
3. `~/.apercode/config.yaml`（ユーザー固有の上書き。差分だけ書けばよい）

`config.yaml` の主な項目:

| 項目 | 内容 |
|---|---|
| `llm.model` | 使うモデル（例: `gemma4:26b`） |
| `llm.tool_mode` | `native`（Ollama tool calling）/ `json`（非対応モデル用フォールバック） |
| `llm.num_ctx` / `llm.auto_ctx.*` | コンテキストサイズの上限と、VRAM の空きからの自動調整（下記） |
| `workspace.root` | エージェントが触れる範囲。この外は拒否される |
| `workspace.default_project` | 新規セッションの既定プロジェクト。空なら最近使ったものを使う |
| `permissions.*` | ツールごとに `allow` / `ask` / `deny` |
| `mt5.*` | WINEPREFIX と MT5 のインストール先 |
| `compaction.*` | コンテキスト圧縮の閾値（num_ctx に対する割合）と、残す直近メッセージ数 |
| `subagents.*` | 子エージェントの上限回数・深さ・モード別モデル |
| `memory.*` | 経験メモリ: 埋め込みモデル、自動注入件数、自動抽出の条件 |
| `web.*` | Web 検索: provider（duckduckgo / searxng）、結果数、取得文字数 |
| `backup.*` | 変更前ファイルの自動バックアップ: フォルダ名、保持日数、対象サイズ上限 |
| `verify.*` | 生成コードの検証レイヤー: 自動チェック・テスト自動実行・レビュー子エージェント（下記） |
| `cloud.*` | クラウド相談: 行き詰まったときにクラウド AI へヒントを求める（下記） |
| `ui.language` / `llm.prompt_language` | 表示言語とプロンプト言語（auto / ja / en。下記） |

## 起動

### デスクトップアプリとして（推奨）

```bash
bash install_desktop.sh
```

アプリメニュー（開発）とデスクトップに「AperCode」が追加される。クリックすると
サーバーを自動起動し（Ollama が止まっていれば `ollama serve` も試みる）、専用ウィンドウを開く。
ウィンドウを閉じるとサーバーも終了する。ログは `~/.apercode/app.log`。

専用ウィンドウの優先順位:
1. pywebview GTK バックエンド（OS の WebKit2GTK。日本語入力がそのまま使える。`bash setup_linux_window.sh` で準備）
2. Chromium / Chrome / Brave の `--app` モード（アドレスバー無しのウィンドウ）
3. pywebview Qt バックエンド（`pip install "pywebview[qt]"`。pip 版 Qt は fcitx 未対応のため日本語入力に難あり）
4. 既定のブラウザ

Linux で日本語入力（Mozc 等）を専用ウィンドウで使うには、1 を推奨:

```bash
bash setup_linux_window.sh   # python3-gi / WebKit2GTK を入れ、.venv を --system-site-packages で作り直す
```

ターミナルから同じ動作をさせるには `python3 app.py`（`--browser` で常に既定ブラウザ）。

#### トラブルシューティング

**専用ウィンドウで日本語入力（Mozc など）が起動しない**

pip でインストールした Qt（`pywebview[qt]`）には fcitx 用の入力メソッドプラグインが含まれていないため、
Qt バックエンドの専用ウィンドウ内では IME が動かない。ブラウザ（Firefox 等）では問題なく入力できるのが特徴。

対策: OS 標準の GTK + WebKit2GTK を使う GTK バックエンドに切り替える。

```bash
bash setup_linux_window.sh
```

このスクリプトは `python3-gi` と WebKit2GTK のバインディングを apt で入れ、仮想環境を
`--system-site-packages` 付きで作り直し（依存パッケージも再インストール）、Qt を外す。
以後 `app.py` は GTK バックエンドを最優先で使うので、OS の日本語入力がそのまま効く。

**専用ウィンドウが開かず、ブラウザで開いてしまう**

`~/.apercode/app.log` に理由が記録される。Qt バックエンドで
`Could not load the Qt platform plugin "xcb"` と出る場合は `sudo apt install -y libxcb-cursor0`。

**「経験メモリに保存」の直後に LLM が応答しなくなる（落ちる）**

v1.1.7 で対策。ターン終了後の教訓抽出（振り返り）はチャットモデルへの追加呼び出しと埋め込みモデル（bge-m3）の
ロードを伴うため、VRAM が足りない環境ではチャットモデルが追い出され、次の応答まで再ロード待ちになったり、
Ollama 自体が落ちたりすることがあった。対策:

- 振り返りを応答完了後の**バックグラウンド**処理にした（会話はすぐ続けられる。失敗しても会話に影響しない、180 秒でタイムアウト）
- 振り返りに渡す記録を 24k 文字に制限、埋め込みモデルは `keep_alive: 2m` で使用後すぐ解放、チャットモデルは
  `llm.keep_alive`（既定 30m）で保持
- Ollama が一時的に応答しない場合は自動で再試行（`llm.connect_retries`、既定 3 回）。途中で切れた場合は
  「LLM との接続が途中で切れました（Ollama が落ちた可能性…）」と表示

それでも落ちる場合は VRAM 不足の可能性が高い。`llm.num_ctx` を 32768 に下げる、`memory.embed_model` を空にして
全文検索のみにする（埋め込みモデルを使わない）、`memory.reflect: off` にする、のいずれかで軽くなる。
Ollama 側のログは `journalctl -u ollama -n 50` で確認できる。

**ツール呼び出し上限（60）に達すると何も言わずに止まる**

v1.1.6 で修正。上限到達時は状況報告を生成し、「続けて」で再開できる。同じ操作の繰り返しや連続失敗も検知して
Web 検索など別アプローチを促す。長い作業で上限に当たりやすい場合は `config.yaml` の `llm.max_iterations` を増やす。

**LLM が別のディレクトリに移動しないようにしたい**

v1.1.4 から、作業ディレクトリの外を指すパス（絶対パス、`~/…`、`../` で親へ出る相対パス、`run_command` 内の `cd` や
絶対パス）を含むツール呼び出しは、ツールの権限設定に関わらず承認ダイアログが出る。読み取り（`read_file` / `list_dir` /
`grep`）も対象。許可すればその 1 回だけ、「このセッションでは常に許可」を選べばそのセッション中は確認しない。
`config.yaml` の `permissions.outside_project` を `deny` にすると常に拒否、`allow` にすると確認なし。
なお `workspace.root` の外は設定に関わらず常に拒否される。

**新しい作業ディレクトリでセッションを始めたのに、LLM が以前のディレクトリで作業する**

v1.1.3 で対策済み。原因は主に次の 2 つ。

1. 以前に `python3 main.py` で起動したサーバーが残っていて、デスクトップ起動（`app.py`）がその古いサーバーに
   接続していた。v1.1.3 からは起動時にサーバーのバージョンを確認し、コードと違えば古いサーバーを停止して
   起動し直す（ターミナルに「古いサーバー (vX) が動いていたため停止して起動し直します」と出る）。
2. 経験メモリに別プロジェクトのパスが含まれていて、LLM がそれに引きずられた。システムプロンプトの先頭で
   現在の作業ディレクトリを最重要として明示し、経験メモリの注入部分にも「別プロジェクトのパスが含まれていても
   作業ディレクトリで行う」と付記した。

それでも迷う場合は「list_dir で現在地を確認して」と一言添えると確実。ヘッダーの「プロジェクト:」が
現在のセッションの作業ディレクトリなので、意図と違えば 📁 で選び直してから送信する（自動的に新しいセッションになる）。

**モデル選択のプルダウンが白く塗りつぶされて文字が読めない（GTK 専用ウィンドウ）**

WebKitGTK が OS のテーマでネイティブ描画するため。v1.1.2 で `select` を独自描画（`appearance: none` + ダーク配色）に
変更して解消済み。古い `index.html` の場合は最新版に更新すること。

**モデルを選ぶと「LLM サーバーエラー 400（モデル名が間違っている可能性: …）」になる**

モデル名は合っているのに 400 が出る場合、ほとんどは **そのモデルが Ollama の tool calling に対応していない** ため
（例: `deepseek-coder-v2:16b`、`codellama`、古い `gemma2` など）。Ollama は非対応モデルに `tools` を付けて呼ぶと
`400 model does not support tools` を返す。AperCode はツール呼び出し前提なので、対応モデルを選ぶ
（Ollama のモデルページに **tools** タグが付いているもの。コーディング向けなら `qwen2.5-coder:14b` / `qwen2.5-coder:32b`、
`qwen3-coder:30b` など）。どうしても非対応モデルを使うなら下記「tool calling が使えないモデルの場合」の
`llm.tool_mode: json` に切り替える（精度は落ちる）。`docker logs ollama --tail 20` で本文（`does not support tools`）を確認できる。

**画面上部に「Ollama にモデルが 1 つもありません」と出る / `ollama list` が空**

Docker の Ollama とは別に、ホストの `ollama serve`（systemd のユーザーサービス）が起動してポート 11434 を先に使っている。
モデルはコンテナ内にあるので消えてはいない（`docker exec ollama ollama list` で確認）。`ss -ltnp | grep 11434` で
`ollama` が表示されたら、`systemctl --user disable --now ollama`（システム側にもあれば `sudo systemctl disable --now ollama`）
で止めて `docker restart ollama`。`ollama pull` も `docker exec ollama ollama pull …` で行う（ホストで pull するとコンテナから見えない）。

**web_search が「HTTP 403」で失敗する**

検索サイトのボット判定です。`ddgs` パッケージを入れると、ブラウザ相当の TLS で接続するため回避できます
（v1.2.1.1 の requirements.txt に含まれています。既存の venv では `.venv/bin/pip install ddgs`）。
入っていれば最初に使われ、失敗しても Bing → Brave → Mojeek → Stack Exchange / GitHub / Wikipedia の
API へ順に切り替わります。結果の 1 行目「検索: …（エンジン名）」でどれが使われたか分かります。
すべて失敗するときはエラー文にエンジンごとの結果が並ぶので、回線側（プロキシ・セキュリティソフト）の
ブロックか判断できます。自前の SearXNG がある場合は `web.searxng_url` を設定してください。

**変換確定の Enter で送信されてしまう**

修正済み（IME 変換中の Enter は無視する）。古い `index.html` を使っている場合は最新版に更新すること。

## 使い方

1. 左上でモデルを選び、作業ディレクトリを指定して「新しいセッション」
   - 📁 ボタンでディレクトリ選択ダイアログ（最近使ったもの・新しいフォルダの作成も可）
   - 存在しないパスを入力すると「新規に作成しますか？」と確認される
   - 選べるのは `workspace.root` 配下のみ
2. 指示を入力（例: 「USDJPY H1 の移動平均クロス EA を作ってコンパイルして」）
3. `write_file` / `edit_file` / `run_command` は承認ダイアログが出る。「このセッションでは編集・実行を常に許可」を押すと、
   そのセッションでは以後のコード生成・編集・テスト実行（`write_file` / `edit_file` / `run_command` / `mt5_*` / `make_icon`）を
   確認なしで続ける（設定はセッションに保存され、再起動後も有効）
   - ただし**取り返しのつかない操作**は常時許可の対象外で毎回確認する: `rm` / `rmdir`、`git reset --hard` / `git clean` /
     `git push --force`、`sudo`、`dd` / `mkfs`、`chmod -R` / `chown`、`kill`、`drop table`、`pip uninstall`、`apt remove`、
     `curl … | sh`、絶対パスへの `mv`、`restore_backup` など（ダイアログに「危険なコマンド」と表示。
     `permissions.dangerous_commands` で正規表現リストを差し替え可能）
   - 作業ディレクトリの**外**（`workspace.root` 内の別ディレクトリ）に触れる操作は、読み取り専用ツールでも必ず承認を求める
     （ダイアログ上部に「⚠ 作業ディレクトリの外へのアクセス: パス」と表示）。`permissions.outside_project` で ask / allow / deny を選べる
   - 承認ダイアログの「**一時停止（質問する）**」（v2.1.0）: 許可も拒否もせずに止める。操作は実行されず、LLM は次の入力を
     質問として答え、その後で操作を続けてよいかを確認する（勝手に再実行しない）。拒否すると LLM が別の方法を探し始めるのを避けたいときに使う
4. ツールカードをクリックすると引数と結果が展開される
5. 「停止」で処理を中断

チャット内のコードのコピー（v1.2.3）:
- 回答中のコードは言語ラベル付きのコードブロックで表示され、右上の「コピー」ボタンで丸ごとクリップボードに入る
- チャット欄で右クリックすると「選択範囲をコピー / コードブロックをコピー / このメッセージをコピー」のメニューが出る
  （キーボードの Ctrl+C も従来どおり使える）

画像やテキストの添付:
- 画像は入力欄に Ctrl+V で貼り付け、またはファイルをドラッグ&ドロップ、📎 ボタンから選択
- 3,000 文字を超えるテキストを貼り付けると、本文ではなく添付（📄）として扱われる
- 画像はセッションごとに `~/.apercode/sessions/<id>_files/` に保存され、直近 2 回分のみ LLM に渡す
- 画像を理解できるのは vision 対応モデル（例: `qwen3-vl`, `gemma3`, `llava`）のみ。非対応モデルでは画像を除いて送信し、その旨を表示する

プロジェクト直下に `AGENT.md`（または `CLAUDE.md`）を置くと、その内容がシステムプロンプトに読み込まれる。EA の命名規則や共通ライブラリの説明などを書いておくと精度が上がる。

## 設定画面（v1.6.0）

画面左の「設定」ボタンから、`config.yaml` を編集せずに主要なパラメータを変更できる。値は `~/.apercode/config.yaml` に保存され
（`config.yaml` より優先）、保存した瞬間に反映される。● が付いた項目は既定から変更済み。「すべて既定に戻す」で `config.yaml` の値に戻る。

| 区分 | 項目 |
|---|---|
| LLM 生成 | 思考モード（`think`: auto / on / off）、生成トークン上限（`num_predict`）、temperature、応答待ち秒数、モデル常駐時間、ツール呼び出し方式、1 入力あたりのツール上限 |
| コンテキスト | VRAM からの自動調整、コンテキスト上限、KV キャッシュ型、予備メモリ、圧縮の開始割合・残す件数 |
| 行き詰まり検知 / 相談 | 同一呼び出し回数、連続エラー回数、進捗なし回数、クラウド相談に必要な失敗数、1 ターンの相談上限 |
| 検証 / その他 | 自動検証、差し戻し上限、レビューの有無と対象行数、サブエージェント、ブラウザ表示、外部サイトの確認、repl の上限秒 |

### 「思考中」で止まるとき

qwen3 などの思考モデルは、思考（`thinking`）だけで生成を終えて本文もツール呼び出しも返さないことがある。v1.6.0 からは
思考がチャットに折りたたみ表示され（🧠 思考 (n 文字)）、思考だけで終わった応答には「結論かツール呼び出しを」と自動で差し戻す。
それでも止まる場合は設定画面で次を試す:

1. **思考モード = off**（最も効く。品質が落ちるモデルもある）
2. **生成トークン上限 = 8192** 程度（思考の暴走を打ち切る。0 は無制限）
3. **応答待ち秒数** を増やす（大きなモデルで最初のトークンまでが長い場合）
4. temperature を 0.1〜0.2 に下げる

### coder 系モデルがコードをチャットに書くだけで実行しないとき

tool calling の学習が弱いモデル（deepseek-coder、codellama 系など）は、ツールを呼ばずにコードや JSON を本文に書いて終わることがある。
v1.6.0 では次の 3 段で対処する: 本文に JSON で書かれたツール呼び出し（```json / ```tool_call / `<tool_call>`）は native モードでも
解析して実行する。コードブロックをチャットに書いただけでファイルを書いていない応答は「write_file / edit_file で書くように」と 1 回差し戻す。
システムプロンプトにも「コードは必ずファイルに書く」と明記した。それでも改善しない場合は tool calling 対応モデル
（qwen2.5-coder / qwen3-coder など）を使うか、設定画面で「ツール呼び出し方式 = json」にする。

## ⚠ 注意: AperCode 自身は AperCode で変更しない（v2.5.0）

AperCode に AperCode 自身（インストール先のフォルダ）や `~/.apercode`（設定・API キー・セッション・経験メモリ）を変更させないでください。
LLM の誤りや、Web・ほかの AI から読んだ内容に仕込まれた指示（プロンプトインジェクション）で自分自身を書き換えると、
安全のための確認や制限そのものが壊れるおそれがあります。AperCode の修正は、ユーザー（またはメンテナー）が AperCode の外で行ってください。

- **自身の保護**: `write_file` / `edit_file` / `restore_backup` などで AperCode のインストール先・`~/.apercode` を変更しようとすると、
  実行せずに断る（作業ディレクトリをその中にしても書き込めない）。LLM には「必要な変更内容をユーザーに報告する」よう返す
- **専用の作業ディレクトリ**（v2.6.0）: AperCode に作業させるときは、専用のディレクトリを作業ディレクトリにし、Python はその中の仮想環境を使う。
  場所は設定画面「AperCode の作業」→「作業ディレクトリ」で変更できる（既定 `~/Documents/Aper_work`、`workspace.default_project`。AperCode 自身の中は指定できない）。
  作業ディレクトリに `.venv`（または `venv`）があれば、コマンド・テスト・`repl` の `python3` / `pip` はその環境になる（PATH の先頭に入れる）
  - 起動時に作業ディレクトリが無い・`.venv` が無いときは、画面上部に案内が出る。「作成する」を押すと、フォルダと仮想環境を作る
    （手動なら `python3 -m venv ~/Documents/Aper_work/.venv`。Ubuntu で失敗するときは `sudo apt install python3-venv`）
- **コマンドのサンドボックス**（Linux、`sudo apt install bubblewrap`）: `run_command`・`process_start`・`repl`・テスト・自動検証を
  bubblewrap の中で実行する。書き込めるのは作業ディレクトリ・`/tmp`・`sandbox.writable`（既定 `~/.cache`, `~/.npm`）だけで、
  ほかは読み取り専用。AperCode 自身は常に読み取り専用、`~/.apercode` は中から見えない
  - 状態はヘッダーに表示する（緑の「🛡 隔離」= 有効、黄色の「⚠ 隔離なし」= 無効・使えない。クリックで設定画面）。設定画面「AperCode の作業」にも表示
  - bubblewrap が入っていないときは、起動時に画面上部へ「sudo apt install bubblewrap」の案内を出す（インストール後は自動で確かめ直す）
  - `sandbox.mode`: `auto`（使えれば使う。既定）/ `on`（必須。使えなければコマンドを実行しない）/ `off`。設定画面「コマンドのサンドボックス」でも変更可
  - `sandbox.network: false` でコマンドのネットワークを遮断。`pip install --user` のような作業ディレクトリの外への書き込みは失敗するので、
    作業ディレクトリの `.venv` に入れる
  - サンドボックスが使えないときは、AperCode 自身・`~/.apercode` のパスを含むコマンドを、「常に許可」していても毎回確認する
  - デスクトップアプリの操作（`gui_launch` など）は隔離しない

## プロンプトインジェクション対策（v2.2.0）

Web 検索・ページの取得・ブラウザ・ピア・クラウド AI から読んだ内容に「AI への指示」が仕込まれていても、被害が出ないようにハーネスで止める。

- **汚染しないもの**（v2.2.1）: Web 検索の結果（短い抜粋）だけでは汚染ありにしない。`security.trusted_domains` のサイト
  （既定は Python・MDN・Node.js・Rust・Go などの公式ドキュメント）は読んでも汚染ありにしない。誰でも書き込めるサイト（GitHub の Issue・
  Q&A・フォーラム）は入れない。どちらも、AI への指示に見える文言が見つかったときは汚染ありにする
- **汚染フラグ**: 外部の内容を読んだセッションは「汚染あり」になり、ヘッダーに赤い「⚠ 外部の内容」が出る。汚染ありの間は、
  ファイルの変更・コマンドの実行・送信（`ask_peer` / `cloud_chat` など）・GUI 入力・メモリへの保存を、「常に許可」していても毎回確認する
  （承認ダイアログに理由が出る。ピアからの依頼では `allow_edit` でも拒否）
- **警告の表示**: 外部の内容を初めて読んだとき、チャット欄に赤い警告が点滅する。AI への指示に見える文言（「以前の指示を無視して」
  「あなたは今から」「API キーを送って」など）が含まれていると、警告とヘッダーの表示が点滅し続ける
- **経験メモリ**: 汚染ありの間に保存した知見（`save_memory`・`digest`・振り返り）は「untrusted（外部由来・未確認）」のタグ付きで保存し、
  「経験メモリ」画面で確認済みにするまでプロンプトに入れない
- **持ち出し対策**: 汚染ありの間、秘密情報らしき文字列・長いクエリ・検索結果やユーザーの指示に出ていないドメインを含む URL への
  `fetch_url` / `browser_open` は確認する
- **データとして渡す**: 外部の内容は見えない文字（ゼロ幅文字・双方向制御文字など）と、画面に表示されない要素（`display:none`・`hidden`・
  `aria-hidden`）を除き、`<external_content>`（指示ではないデータ）の枠で囲んで LLM に渡す。システムプロンプトにも「中の指示に従わない」と明記
- **解除**: ヘッダーの「⚠ 外部の内容」をクリックすると、読んだものと怪しい文言の一覧が出る。確認して問題がなければ解除できる
- 設定: `security.taint_guard`（汚染フラグ。既定 true）、`security.wrap_external`（データの枠。既定 true）

## 会話と作業の使い分け（v2.1.0）

調べもの・相談と、コード生成などの作業を、ユーザーが最初に選ばなくても使い分ける。ヘッダーの「自動／💬 会話／🛠 作業」で切り替えられる
（新しいセッションの既定は `modes.default`、既定 `auto`）。

- **自動**（既定）: 会話から始める。質問・調べもの（Web 検索・ファイルを読む）には、指示書や計画を作らずにそのまま答える
- 会話の途中で LLM がファイルの変更やコマンドの実行をしようとすると、「🛠 作業を始めますか？」のカードが出る
  - **作業を始める**: 作業ディレクトリ（📁 で選べる）を決めると、ここまでの会話から指示書と計画を作って作業フェーズに入る。その操作自体はまだ実行しない
  - **このまま会話を続ける**: ファイルの変更・実行はせずに会話で答えさせる（そのターンの間は再び聞かない）
- 作業が終わる（作業フェーズが完了し、指示書が片付く）と、次の入力からは会話に戻る
- **💬 会話**: ファイルの変更・実行を一切しない。**🛠 作業**: 最初から作業として扱う（v2.0 までの動き）

## 作業の指示書（v1.8.0）

ローカル LLM は、長い作業の途中で最初の目的を忘れやすい。AperCode は最初の指示を「作業の指示書」として Markdown に清書し
（`<プロジェクト>/.apercode/briefs/<セッションID>.md`）、LLM を呼ぶたびにファイルを読み直してシステムプロンプトに添える。

- 指示書は「目的・要件・制約・完了条件」とユーザーの原文。清書でユーザーが書いていない要件は足さない
- LLM に読みに行かせるのではなく AperCode が毎回添えるので、読み忘れが起きない。会話履歴の圧縮（要約）でも失われない
- 2 回目以降の指示は「追加・変更の指示」として追記される（「続けて」などの短い返事は除く）
- ヘッダーの「📋 指示書」から内容を確認・編集できる。編集は次の LLM 呼び出しから反映される
- 目的を達成すると、LLM が `finish_brief` ツールで指示書を削除する（テスト失敗・自動検証 NG が残っている間は削除できない）。
  画面から「削除（目的を完了にする）」でも消せる。次の指示で新しい指示書が作られる
- 無効にするには設定画面の「作業の指示書」をオフにする（`brief.enabled: false`）

## 作業フェーズとチェックポイント（v1.9.0）

ローカル LLM は「次に何をするか」を毎回自分で決めると脱線しやすく、壊れた状態の上に修正を重ねてエラーループに入りやすい。
AperCode は今のフェーズと手順を自分で持ち、フェーズごとに短い指示と使えるツールを切り替える。フェーズを進めるのは LLM ではなく AperCode。

| フェーズ | LLM に渡す指示 | 使えるツール | 次へ進む条件（AperCode が判定） |
|---|---|---|---|
| 計画 | 調べて手順を 3〜7 個に分ける | 読み取り系 + `set_plan` | 手順が登録された（変更不要な質問ならそのまま回答して終了） |
| 実装 | 手順 n だけを実装する | 書き込み・実行系 + `step_done` | `step_done`（または本文だけの応答） |
| 検証 | （LLM は呼ばない） | - | 自動検証・テストが通る → チェックポイントを保存して次の手順 / 失敗 → 修正 |
| 修正 | このエラーだけを直す | 書き込み・実行系 + `step_done` | 再検証が通る / 上限回数を超えた → 巻き戻して調査 |
| 調査 | 原因を調べ、別の方針を書く | 読み取り系・Web 検索・クラウド相談 | 方針が書かれた → その方針で実装をやり直す |
| 完了確認 | 指示書の完了条件を確認する | 読み取り系・テスト・`finish_brief`・`set_plan` | 完了報告 / 足りない手順を追加 |
| 報告 | 状況をユーザーに報告する | なし | 「続けて」で同じ手順から再開 |

- チェックポイントは作業開始時と、各手順の検証が通るたびに `<プロジェクト>/.apercode/checkpoints/<セッションID>/` に保存される
  （AperCode が write_file / edit_file で変更したファイルが対象。子エージェントの変更も含む。`run_command` による変更は追跡しない）
- 修正を `phases.max_fix_rounds`（既定 3）回重ねても通らないと、直前のチェックポイントへファイルを戻し、
  その後の失敗した試行を LLM の履歴から外してから調査フェーズに入る。壊れた状態の上に修正を重ねる悪循環を断ち、コンテキストも軽くなる
- 巻き戻し → 調査 → やり直しが `phases.max_investigations`（既定 1）回を超えると、最後に検証が通った状態のまま報告して止まる
- ヘッダーの「🧭」チップに今のフェーズと手順（例: 🧭 修正 2/5）が出る。クリックで計画とチェックポイントの一覧を開き、
  「この時点に戻す」でファイルと会話をその時点に戻せる（戻す前のファイルは backup/ に退避）
- 2 回目以降の指示では残りの手順を計画し直す。「続けて」は途中から再開
- 計画に必要な情報が足りないとき（ファイルが読めない等）、LLM はユーザーに質問して止まる。返事を送ると計画フェーズから続く（v1.9.1）
- 作業中のヒント・追加の指示では計画を立て直さず、今の手順を続ける（残りの手順が合わなければ LLM が `set_plan` で出し直す）。「最初から」「やり直し」で計画を作り直す（v1.11.0）
- アプリ操作など、ファイルを変えていない手順で行き詰まったときは、巻き戻し・調査フェーズを挟まず別のやり方でやり直させる（v1.11.0）
- 書いたスクリプトがテストで実行されていないときは、一度実行して確かめるまで完了にしない（v1.11.0）
- コマンド実行・GUI 操作など、テストで確かめられない手順は「操作した」だけでは完了にならない。AperCode が結果の観察（GUI ならアプリ全体のスクリーンショット、コマンドなら出力）を求め、観察した後に `step_done` の evidence へ「何を見て成功と判断したか」を書いたときだけ次へ進む（v1.10.1、`phases.require_evidence`）。操作の後に既にスクリーンショットなどで確かめ、evidence を書いていれば、撮り直しなしで 1 回で進む（v1.11.1）。完了確認では、最後に観察した画面や出力（相手の返信など）に、まだ応えていない依頼や質問が残っていないかも確かめる（v1.11.2）
- 無効にするには設定画面の「作業フェーズ」をオフにする（`phases.enabled: false`）。テストが遅いプロジェクトでは「手順ごとにテスト」をオフに

## デスクトップアプリの操作（v1.11.0、Linux / X11）

ブラウザではないデスクトップアプリ（Claude デスクトップアプリなど）を、決まった手順で確実に操作するツール。
LLM がその場で xdotool・xclip・Xlib のスクリプトを組み立てると、起動コマンドの書き誤り・クリップボードの扱い・
座標のずれ・フォーカス外れで失敗しやすいため、手順をツールとして固定した。

| ツール | 内容 |
|---|---|
| `gui_windows` | 開いているウィンドウの一覧（ID・位置・大きさ・タイトル・アクティブか） |
| `gui_launch(command, title)` | アプリを起動し、ウィンドウが現れるまで待つ。既に開いていれば起動しない |
| `gui_activate(window)` | 前面に出してアクティブにし、本当にアクティブになったかを確かめる |
| `screenshot(window)` | ウィンドウ（省略で画面全体）を撮って、画像として LLM に直接渡す（ブラウザで開き直す必要はない） |
| `gui_input(window, click, text, keys)` | 前面に出してから、クリック → 文章の貼り付け（日本語可） → キー入力 |

- `window` はタイトルの一部（例: `Claude`）か `0x` で始まるウィンドウ ID
- 文章を Enter で送ると、相手の返事を見る前に `gui.reply_wait`（既定 10 秒）待つ（v2.4.0）。会話の相手の状態（書き途中・返事済み・
  相手側のユーザーの承認待ち）を見分け、書き途中や承認待ちの間は送らずに待つ。相手の許可ボタンは押さない
- `click` は直前の `screenshot` の画像上の座標。撮影時の縮小率といまのウィンドウ位置で画面座標に直すので、ウィンドウが動いても押せる
- スクリーンショットは画面全体を撮ってウィンドウの位置で切り出す（Electron のウィンドウは単体で撮ると壁紙しか写らないことがある）
- 入力は xdotool → xte → python-xlib の順に、使えるものを自動で選ぶ
- 承認ダイアログで AperCode が前面に出ても、承認後に元のウィンドウへ戻してから実行する（`permissions.restore_focus`）。
  見ていない間に操作させるときは、承認で「このセッションでは編集・実行を常に許可」を選ぶと止まらない
- 必要なもの: `sudo apt install wmctrl x11-utils xclip imagemagick` と、入力用に `xdotool` / `xautomation` / `python3-xlib` のどれか。Wayland のみの環境では使えない

## ほかの AI との協調（v2.0.0）

AperCode を「ほかの AI と組んで成果を出す」ための機能。LAN 上の別の AperCode に作業を任せたり、クラウド AI と議論したりできる。
相手の返事を読み飛ばさないこと、指示書の不足を作業前に確かめることもハーネスで担保する。

### 会話の消化（digest）
- `set_plan` の `kind` に `converse`（ほかの AI や人との会話）を追加
- 会話の相手の返事を受け取ったら、次を送る前に `digest` を呼ぶことを AperCode が求める。整理しないまま送ろうとすると送信を止める
  （チャットアプリへの `gui_input` の入力・`ask_peer` / `peer_reply` / `cloud_chat`）
- `digest` には、相手の言いたいこと・助言・訂正・自分への指摘（`points`）、質問すべて（`questions`、前からの未回答も含む）、
  返信の方針（`reply_plan`）、今後に役立つ知見（`insights`）を書く。知見は経験メモリに保存され、次の作業で使われる
- 会話の手順でファイルを変えていなければ、手順の検証でテストを走らせない（作業ディレクトリにある無関係のテストを直させないため）。
  会話の実験などは、無関係なファイルの無い専用のディレクトリで行うのがよい。相手へ 1 回送るごとにツール呼び出しの上限を延ばす（v2.3.1）
- 会話の回数（v2.3.0）: 「3 回会話して」のように回数を指定すると、それを目安として数える。目安を超えて送ろうとすると、
  AperCode が理由（相手の未回答の質問・返信の方針）を示して「💬 会話を続けますか？」と許可を求める。許可すればその 1 回を送り、
  拒否すれば送らずに、未回答の質問が残っていることを完了報告に書く。超えた場合は完了報告にその理由が書かれる
- 未回答の質問は実装フェーズの指示に残り続ける。完了確認で相手の最後の返事が未整理なら、1 度だけ整理を求める
- `digest` は返事 1 通につき 1 回。同じ返事を整理し直そうとすると、返信へ進むよう返す。返事を待つ `sleep` は「繰り返し」に数えない（v2.0.1）

### 指示書の不足点検（`brief.clarify`）
- 作業の指示書を作った直後に、完了条件（会話・繰り返し作業では終了条件）・対象・取り返しのつかない操作の範囲・成果物の形式を点検する
- AperCode が自分で決めると大きな手戻りや損害になる不足は、作業を始める前にユーザーへ質問して止まる（最大 3 つ）。
  返事（短くてもよい）は指示書に追記され、そのまま作業が始まる
- 細かい点・やり方（アプリの起動方法や使うツールなど）は質問せず「AperCode の仮定」として指示書に書く（違っていれば指示で直せる）。終了条件が相手の行動だけに頼っているときは、来なかった場合の上限（往復数・時間）も仮定として書く（v2.0.1）
- `brief.clarify: assume` にすると質問せずに仮定を書いて進む（見ていない間に動かすとき向け）。`off` で点検しない

### ピア（LAN 上の別の AperCode）
受け側（作業を任される AperCode）の `config.yaml`（または `~/.apercode/config.yaml`）:

```yaml
peer:
  enabled: true
  host: 0.0.0.0            # LAN から受ける
  port: 8766
  token: "推測されにくい長い文字列"
  projects: [~/Documents/AperCode_next]   # 依頼を受け付けるプロジェクト
  on_approval: allow_edit  # 編集・テスト実行は許可。危険なコマンド・プロジェクト外・GUI は拒否（既定 deny）
```

依頼側（任せる AperCode）:

```yaml
peers:
  - name: bunke
    url: http://192.168.1.20:8766
    token: "受け側と同じ文字列"
```

| ツール | 内容 |
|---|---|
| `peer_list` | 設定済みのピアの状態（バージョン・モデル・受け付けるプロジェクト） |
| `ask_peer(peer, task, project, mode, files)` | 作業を依頼し、終わるまで待って相手の応答を返す。`mode=explore` は読み取りだけ。`files` で自分のファイルを送れる（相手の `.apercode/inbox/` に置かれ、上書きはされない） |
| `peer_reply(peer, task_id, text)` | 相手の質問に答える・修正を頼む |
| `peer_status(peer, task_id)` | 実行中の依頼の状態を見る |
| `peer_read_file(peer, project, path)` | 相手のファイルを読む（報告の裏取り・レビュー） |
| `peer_verify(peer, project)` | 相手のプロジェクトでテストを実行して結果を返す |
| `cloud_chat(message)` | クラウド AI と会話する。`ask_cloud` と違い、行き詰まっていなくても使える（送信前に承認） |

- ピア API は画面用サーバーとは別のポートで待ち受け、ピア用のエンドポイントだけを公開する。`peer.token` が無いリクエストは拒否する。`peer.token` か `peer.projects` が空なら起動しない。ポートが使えないときは画面用サーバーは止めずに警告だけ出す
- 依頼を受け付けるのは `peer.projects` の中だけ。AperCode のデータ（`~/.apercode`：設定・API キー・セッション）とドットで始まるフォルダ・ファイル（`.ssh`・`.env` など）は常に対象外
- 依頼は受け側の LLM・ツール・権限で実行する。承認が必要な操作は `peer.on_approval` に従う（`deny` / `allow_edit` / `allow`）。コマンド実行・GUI・ブラウザ・`fetch_url` などは、受け側の `permissions` が allow でも必ずこの方針に通す。ピアからの依頼の中では `ask_peer` などのピア用ツールと `cloud_chat` は使えない（子エージェントも同じ）。API から任意のコマンドは受け付けず、テストは自動検出したコマンドだけを実行する
- 依頼されたセッションは受け側の画面のセッション一覧にも `[依頼元の名前]` 付きで残る
- 受け側も作業前の点検で質問してくることがある。その返事は依頼側が `peer_reply` で送る
- 通信は平文の HTTP。信頼できる LAN の中だけで使う

## 表示言語（v1.3.0）

日本語と英語を内蔵し、実行時に切り替えられる。既定は `auto`（OS の言語 `LANG` が日本語なら日本語、それ以外は英語）。

- 画面左下の「言語」プルダウン（自動 / 日本語 / 英語）で切り替え。`~/.apercode/config.yaml` の `ui.language` に保存され、画面が再読み込みされる
- 「プロンプト言語」プルダウン（`llm.prompt_language`）は LLM へのシステムプロンプトの言語。`auto` は表示言語に合わせる。
  英語プロンプトにはローカルモデルの指示追従が安定する利点があり、回答はユーザーの入力言語で返すよう指示してあるので、
  日本語表示 + 英語プロンプトという組み合わせも使える
- 英語表示では、画面・承認ダイアログ・検証結果・差し戻し文・ツールの結果やエラー・ツールの説明（LLM に渡すスキーマ）が英語になる
- 経験メモリの教訓は保存時の言語のまま（bge-m3 は多言語なので、日本語の教訓を英語で検索しても当たる）
- 他の言語を追加するには、`codeagent/i18n.py` の `MSG_EN` / `TOOL_EN` と `index.html` の `I18N_EN` に相当する辞書を追加する

## コンテキスト圧縮

履歴の推定トークン数（または直近の実測値）が `num_ctx × compaction.threshold` を超えると、
直近 `keep_recent` 件を残して古い履歴を LLM で要約し、1 メッセージに置き換える。
要約リクエストは `num_ctx` の 4 割程度の文字数に抑え、長い記録は分割して段階的に要約する（v1.2.5。
一度に送りすぎて Ollama が落ちるのを防ぐ）。それでも落ちる場合は `compaction.threshold` を 0.6 に下げる。
元のメッセージはセッション JSON の `archive` に保存される。
ヘッダー右上のメーターで現在の使用量を確認でき、「要約」ボタンで手動実行もできる。

## サブエージェント

親エージェントは `spawn_agent` ツールで子エージェントにサブタスクを委譲できる。
子は独立した会話履歴で動き、完了時に「結果報告」だけを親に返すので、親のコンテキストを消費しない。

- `mode=explore`: 読み取り専用（read_file / list_dir / glob / grep）。既存コードの調査向け
- `mode=code`: 編集・コマンド実行可。独立したモジュールの実装向け

承認が必要な操作は子でも同じように UI に承認ダイアログが出る。

### メインとサブのモデルを画面で選ぶ（v1.2.2）

チャットではどちらが動いているか色で分かる（v1.5.1）: メイン LLM の回答は青の左線、サブ LLM（子エージェント・レビュー）は
紫の左線と「サブ LLM · モデル名 · mode」のバッジ、Web 検索は緑、クラウド相談は橙のカード。ログ上部に凡例がある。


左上に 2 つのプルダウンがある。上が **メインモデル**（会話・実装）、下が **サブモデル**（サブエージェントの調査・実装、
コードレビュー用）。サブに 8B クラスの軽いモデル（例: `llama3.1:8b`）を指定すると、調査やレビューが速くなり、
27B と 8B が同時に VRAM に載っていれば切り替えのロード待ちも無い。「サブ: メインLLMを使う」（既定）にすると 1 モデル運用になり、サブ LLM は不要。
選択は `~/.apercode/state.json` に記憶され、次回起動時も引き継がれる（`config.yaml` の `llm.model` /
`subagents.*_model` より優先。config の値に戻すには state.json の `model` / `sub_model` を削除する）。
ヘッダーに「モデル: qwen3.8:27b ／ サブ: llama3.1:8b」のように現在の組み合わせが出る。
画面で選ばない場合は `subagents.explore_model` / `code_model` / `verify.review.model` の設定が使われる。

### サブ LLM の役割（v1.6.1）

サブ LLM（画面の「サブ」で選んだモデル）は次の 4 つに使われる。どれもメイン LLM の手を止めない・メインの文脈を汚さないための仕事。

| 役割 | 内容 |
|---|---|
| 子エージェント（`spawn_agent`） | 調査（explore）・実装（code）を別コンテキストで行い、結果だけ親に返す |
| コードレビュー | 変更が大きいとき diff を読んで high / medium の指摘を返す |
| **背景要約**（v1.6.1） | 履歴が圧縮開始の 75% に達したら、バックグラウンドで古い履歴の要約を先に作る。メインは作業を続け、圧縮が必要になった瞬間に待ち時間なしで差し替える |
| **教訓抽出**（v1.6.1） | ターン終了後の経験メモリへの教訓抽出。メインを次の入力のために空けておく |

背景要約の実行場所は `compaction.bg_device`（設定画面の「サブ LLM の実行場所」）で選ぶ。`auto`（既定）は、空き VRAM に
サブ LLM とその KV キャッシュが載るなら GPU、載らなければ CPU で動かす。メイン LLM が VRAM の大半を使っている構成
（auto_ctx でコンテキストを最大にしている場合など）では CPU になり、要約に時間はかかるが、メインを VRAM から追い出して
再ロードさせることはない。サブを「メイン LLM を使う」にしている場合、背景要約は行わない（同じモデルに同時に投げると
メインの応答が遅れるため）。

## 経験メモリ

成功・失敗の教訓や環境固有の事実を蓄積し、次のタスクで自動的に参照する。分野（言語・ツール）に依存しない。

- 保存単位: `状況 / 行動 / 結果(成功・失敗・事実) / 教訓 / タグ / プロジェクト / 確認済みフラグ`
- 蓄積の経路
  - 自動: ツールを `reflect_min_tools` 回以上使ったターンの終了後、LLM が作業記録から教訓を抽出して保存（`memory.reflect: auto`）
  - エージェント自身: `save_memory` ツール
  - 手動: 左メニュー「経験メモリ」から追加・編集・削除・確認済み設定
- 参照の経路
  - 自動: ユーザー入力ごとに関連する経験を検索し、上位 `inject_top_k` 件をシステムプロンプトに注入（画面に「参照した経験」と表示）
  - エージェント自身: `search_memory` ツール
- 検索: 埋め込みベクトル（Ollama `bge-m3`）と全文検索（FTS5 trigram）のハイブリッド。プロジェクトの言語タグ一致・確認済みにボーナス
- 類似度 `dedup_threshold` 以上の既存メモリがあれば重複として保存しない

埋め込みモデルの準備:

```bash
ollama pull bge-m3
```

モデルが無い場合は全文検索のみで動作する（「経験メモリ」画面に「利用不可」と表示される）。
`embed_model` を変えたら「再索引」ボタンで埋め込みを再計算する。

自動抽出された教訓は `verified=0`（未確認）で保存される。管理画面で「確認済にする」を押すと検索時に優先される。
誤った教訓は削除すること。DB は `~/.apercode/memory.sqlite`（1 ファイル、バックアップはコピーするだけ）。

**埋め込みモデルが使えないとき（v1.6.2）**: bge-m3 が Ollama に無い・応答しない間は全文検索だけで動作し、その間に保存した
教訓はベクトル無しで保存される。bge-m3 が使えるようになると自動でベクトル化される（検索・保存のたび、および
`memory.embed_retry_interval` 秒ごとに確認）。画面上部に「埋め込みモデル bge-m3 が Ollama にありません」と警告が出たら、
`docker exec ollama ollama list` でコンテナ内にあるかを確認する。コンテナ内にあるのに警告が出る場合は、ホスト側の
`ollama serve` がポート 11434 を使っている（トラブルシューティング参照）。

## コンテキストサイズの自動調整（v1.1.8）

起動時とモデル切替時に、空き VRAM（GPU が無ければ空き RAM）とモデルの構造（層数・KV ヘッド数・ヘッド次元）から
KV キャッシュに使えるトークン数を見積もり、`llm.num_ctx` を上限としてコンテキストサイズを自動で決める。
画面に「コンテキストサイズを自動設定: N tokens（GPU 空き … − モデル … → 約 … tokens）」と表示され、
ヘッダーのモデル名にマウスを乗せると計算根拠が見える。
GPU が複数ある場合は全 GPU の空き容量を合算する（Ollama は層を複数 GPU に分散して載せる）。予備は GPU ごとに確保する。

```
KV キャッシュ/トークン = 2 × 層数 × KV ヘッド数 × ヘッド次元 × 2 byte (f16)
使えるメモリ = 空き VRAM − モデル本体 − 予備 (reserve_mb)
num_ctx = 使えるメモリ × 0.8 ÷ KV/トークン → 4096 の倍数に切り下げ、min〜上限で丸める
```

`config.yaml` の `llm.auto_ctx`:

| 項目 | 内容 |
|---|---|
| `enabled` | 自動調整のオン/オフ（オフなら `num_ctx` をそのまま使う） |
| `min` / `max` | 下限 / 上限（`max: 0` なら `num_ctx` が上限） |
| `reserve_mb` | 計算用に空けておく予備メモリ（既定 1024） |
| `kv_cache_type` | Ollama の `OLLAMA_KV_CACHE_TYPE` に合わせる。`q8_0` なら約 2 倍のコンテキストが載る |
| `ram_offload_ratio` | 0 より大きいと空き RAM のこの割合も KV 用に数える（GPU に載りきらない分を RAM に逃がす前提。遅くなる） |

目安: 27B Q4（約 17 GB）を 24 GB の GPU で使う場合、f16 KV では 12k 前後、`q8_0` なら 24k 前後になる。
設定の 64k をそのまま使うと GPU に載りきらず RAM に退避されて極端に遅くなったり、Ollama が落ちたりするので、
自動調整の値を基準にし、必要なら `kv_cache_type: q8_0`（Ollama 側で `OLLAMA_KV_CACHE_TYPE=q8_0` と
`OLLAMA_FLASH_ATTENTION=1` を設定）で増やすのが安全。

**Ollama が別マシンのとき（v1.6.3）**: `llm.base_url` が LAN の別マシン（例: `http://192.168.11.9:11434`）だと、このマシンの GPU では
そのマシンの空き VRAM が分からない。設定画面の「リモート GPU の VRAM 合計 (MB)」にそのマシンの GPU の合計（16GB+12GB なら 28672）を
入れると、そこからロード中の他モデル分を引いた空きでコンテキストサイズを自動調整する。0 のままなら「コンテキスト上限」の値をそのまま使う。

## 生成コードの検証レイヤー（v1.2.0）

「書く → 検証 → 直す → レビュー」のループをシステム側で回し、人が承認しなくても壊れたコードが残りにくくする。
EA（MQL5）はコンパイラとバックテストで検証できるが、Python や他の言語のアプリにも同じ仕組みを用意したもの。

```
ユーザー指示 → 実装 → [自動チェック] NG なら差し戻し（最大 max_fix_rounds 回）
           → 完了報告の直前に [テスト自動実行] 失敗なら差し戻し
           → 変更が大きければ [レビュー子エージェント] 指摘があれば差し戻し
           → 完了報告 + 画面に「検証結果」サマリ
```

1. **自動チェック**: `write_file` / `edit_file` の直後に、拡張子に応じて構文・lint・型チェックを実行し、
   結果をツール結果の末尾（`## 自動検証`）として LLM に返す。NG なら「修正してから進む」よう指示する。
   外部ツールは「入っていれば使う」方式（無ければ構文チェックのみ）。

   | 言語 | 構文 | lint / 型（入っていれば） |
   |---|---|---|
   | Python | `py_compile` | `ruff`（未定義名・未使用 import 等の F/E9 ルールのみ）/ `pyflakes`、構造チェック（組み込み）、`pyright` / `mypy`（v1.10.0） |
   | JS / TS | `node --check` / `tsc --noEmit` | `eslint`（設定ファイルがあるとき） |
   | Go | `go vet` | |
   | Rust | `cargo check` | |
   | シェル | `bash -n` | `shellcheck` |
   | C / C++ | `gcc/g++ -fsyntax-only` | |
   | JSON / YAML | パース | |

2. **テストの自動実行**（`run_tests` ツール）: LLM が完了報告をしようとした時点で、まだテストを実行していなければ
   システムがテストを走らせる。コマンドはプロジェクト構成から自動判定（`pytest` / `unittest` / `npm test` /
   `go test` / `cargo test` / `make test`。`backup/` は収集対象外）。失敗すれば失敗内容を LLM に戻して修正させる。
   テストが無いプロジェクトでは、変更した機能に対する最小限のテストの作成を 1 回促す
   （`verify.create_missing_tests: false` で無効）。LLM が `run_command` で自分でテストを走らせた場合も「テスト済み」と扱う。

3. **レビュー子エージェント**: 変更行数が `verify.review.min_changed_lines`（既定 50）以上のとき、読み取り専用の
   子エージェントが今回の差分（unified diff）をレビューし、バグ・未処理例外・呼び出し元との不整合・要件漏れ・
   セキュリティを high / medium / low で指摘する。high / medium があれば親に【レビュー指摘】として戻して修正させ、
   もう一度レビューする（`max_rounds`、既定 2）。小さな修正では走らないので LLM 呼び出しの増加は限定的。
   `verify.review.model` で軽いモデルをレビュー専用に指定できる。

4. **テストの保護（v1.2.1）**: 「失敗 → 修正」ループの罠は、実装ではなくテストの方をパッチに合わせて書き換えて
   通してしまうこと（assertion weakening）。これを防ぐため、そのターンでテストが一度失敗した後は、既存テストファイル
   （`tests/`, `test_*.py`, `*_test.py`, `*.spec.ts`, `conftest.py` など。`verify.test_patterns` で変更可）への
   `write_file` / `edit_file` と、テストパスを書き換えるシェルコマンド（`sed -i`, `>`, `rm`, `mv` …）を
   「常時許可」の対象外にし、毎回承認を求める（`verify.lock_tests: ask`）。`deny` にすると拒否して実装側の修正を
   指示する。新しいテストの追加は制限しない。さらに、テストが通った時点でターン開始時からの既存テストの変更・削除を
   検出し、「⚠ 既存テスト変更 N 件」として検証結果に表示する。
   また、テストが失敗したまま何も変更せずに完了報告しようとした場合は、再実行せずにそのまま差し戻す。

完了時に画面へ「検証結果 変更 N ファイル / M 行 ｜ 自動チェック x 回（NG y） ｜ テスト: PASS … ｜ レビュー: 指摘なし」
のサマリが出る。各行をクリックすると詳細（エラー出力・指摘内容）が開く。

`config.yaml` の `verify`:

| 項目 | 内容 |
|---|---|
| `enabled` | 検証レイヤー全体のオン/オフ |
| `lint` | `auto`（入っているツールを使う）/ `off`（write/edit 後のチェックをしない） |
| `types` | `auto`（既定）: `pyright`（無ければ `mypy`）が入っていれば、変更した行の「実行すると落ちる」種類の誤りだけを NG にする / `off` |
| `structure` | 組み込みの構造チェック（存在しない `self.xxx`・引数の数の誤り）。今回の変更で増えた問題だけ（既定 `true`） |
| `coverage` / `coverage_min_lines` | `auto`: 変更した行がテストで一度も実行されていなければテストの追加を 1 回求める / `off`。求める最小行数（既定 3） |
| `tests` | `auto`（完了前に自動実行）/ `off` |
| `create_missing_tests` | テストが無いときに作成を促す |
| `max_fix_rounds` | 自動チェック NG / テスト失敗の差し戻し回数上限（既定 3） |
| `review.enabled` / `min_changed_lines` / `max_rounds` / `model` | レビューの有効化、対象となる変更行数、回数、使用モデル |
| `lock_tests` / `test_patterns` | テスト失敗後の既存テスト変更: `ask`（要承認）/ `deny` / `off`。テストと見なすパスの正規表現 |

`requirements.txt` に `ruff` と `pytest` を追加した。既存の venv では `pip install ruff pytest` を実行する。

### 検証の強化（v1.10.0）

構文チェック・lint・既存テストをすべて通るのに、実行すると落ちるバグがある（v1.9.0 を分家へ移植したとき、
存在しないメソッド `self._phase_gate` を呼ぶコードが入った）。これを防ぐために 3 つを加えた。

- **構造チェック（追加ツール不要）**: Python の AST を調べ、そのクラスのどこにも定義されていない `self.xxx` の参照と、
  同じクラスのメソッド・同じファイルの関数の呼び出しで引数の数やキーワード名が定義と合わないものを NG にする。
  継承しているクラス・ミックスイン・`__getattr__` や `setattr` を使うクラスは誤検出を避けるため調べない。
  既存コードの問題で毎回 NG にならないよう、変更前にも同じ問題があったものは報告しない
- **型チェック（入っていれば）**: `pyright`（無ければ `mypy`）で、今回変更した行の「存在しない属性・未定義名・
  引数の誤り」など実行時に落ちる種類の誤りだけを NG にする（型注釈の不足やスタイルでは NG にしない）。
  `pip install pyright` または `pip install mypy` で有効になる
- **変更行のカバレッジ（`coverage` が入っていれば）**: テストを `coverage run -m pytest` で実行し、テストは通ったが
  今回変更した行が一度も実行されていなければ、その行を示してテストの追加を 1 回求める（作業フェーズでは手順ごと）。
  `if __name__ == "__main__":` の中は対象外。テストで実行できない理由（GUI・外部サービスなど）があれば LLM がその旨を書いて先へ進む。
  `pip install coverage` で有効になる（Python のプロジェクトで pytest を使う場合のみ）

## ハーネスの回帰テストとベンチマーク（v1.10.0）

AperCode 自身の改修で性能が落ちていないかを確かめる仕組み。

**回帰テスト**（`tests/`）: 台本どおりに応答する偽の LLM でエージェントループを動かし、作業フェーズの進み方・
フェーズごとのツール制限・検証・巻き戻し・チェックポイント・構造チェック・カバレッジなどが正しく動くかを確かめる
（LLM の出来に左右されない。数秒で終わる）。AperCode のフォルダで:

```bash
pip install pytest coverage      # coverage は無くても可（関係するテストだけ飛ばす）
python -m pytest
```

AperCode 自身を AperCode で改修するときは、このテストが自動検証で毎回実行される。

**ベンチマーク**（`bench/`）: 実際のローカル LLM に 10 個の小さな課題（関数の実装・バグ修正・CLI オプション追加・
CSV 集計・名前の一括変更・テストの作成・クラスへのメソッド追加・JavaScript の修正・設定のマージ・複数ファイルにまたがる機能追加）
を解かせ、LLM には見せない受け入れテストで合否を判定する。テストの作成課題では、実装をわざと壊したときに
書いたテストが失敗するか（変異テスト）まで確かめる。

```bash
python bench/run_bench.py                    # 全課題（モデルは画面で選んだもの）
python bench/run_bench.py --tasks 01,06 --repeat 3
python bench/run_bench.py --phases off --label フェーズなし   # 作業フェーズの効果を比べる
python bench/run_bench.py --history          # 過去の結果の一覧
```

結果は `bench/results.jsonl` に追記され、成功率・平均時間・ツール呼び出し回数・修正回数・巻き戻し回数・トークン数を記録する。
実行の最後に同じモデルの前回の結果と成功率を比べて表示する。LLM の出来にはばらつきがあるので、比較には `--repeat 3` 以上を勧める。

- ツールは自動で許可する（作業は一時フォルダの中だけ。作業フォルダの外に触れる操作は拒否）
- 経験メモリ・ブラウザ・クラウド相談は切る（ベンチマークの教訓がふだんの記憶に混ざらないように）
- コンテキストサイズは設定値を使う。画面の自動調整とそろえるときは `--num-ctx` で指定する
- 課題を追加・変更したら `python bench/validate_tasks.py` で、受け入れテストが「最初は不合格・正しい解答なら合格」になるかを確かめる

## クラウド相談（v1.2.4）

ローカル LLM が Web 検索をしても解決できないとき、クラウドの強いモデルに **ヒントだけ** を求める仕組み
（`ask_cloud` ツール）。会話全体を渡すのではなく、「目的・エラー全文・試したことと結果・関連コードの抜粋（最大 6 ファイル、
各 200 行まで）・質問」を 1 回の単発リクエストで送り、「原因の仮説・確認方法・修正案（diff）」を受け取る。
実装と検証はローカル側が行うので、テストやレビューのゲートはそのまま効く。

設定は左の「クラウド相談」ボタンから（`~/.apercode/config.yaml` の `cloud:` に保存、API キーを含むためパーミッション 600）。
`config.yaml` の `cloud:` に直接書いても同じ。

| 項目 | 内容 |
|---|---|
| プロバイダ | Anthropic Claude / Google Gemini / OpenAI / DeepSeek / Groq / Mistral / OpenRouter / xAI / OpenAI 互換（カスタム URL） |
| モデル | プルダウンの代表モデルから選ぶか手入力 |
| API キー | 未入力なら環境変数（`ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `OPENAI_API_KEY` …）を使う |
| 接続テスト | 保存してから短いリクエストを送り、疎通とキーの有効性を確認 |

安全弁（`config.yaml` の `cloud.*`）:

- `require_failures`（既定 1）: 自動検証の差し戻し・テスト失敗・行き詰まり検知（進捗なし検知を含む）の合計がこの回数に達するまで `ask_cloud` は使えない
  （先にローカルで粘らせる）。クラウド相談が無効のときは、ツール自体が LLM に見えない
- `max_per_turn`（既定 2）: 1 ターンの相談回数上限
- `permissions.ask_cloud: ask`（既定）: 送信前に承認ダイアログが出る（送る目的・エラー・試したこと・対象ファイルが見える）
- `mask_secrets`（既定 true）: `api_key=…`、`sk-…`、`AIza…`、秘密鍵などを送信前に `<masked>` に置換
- 相談の返答には「ヒントなので裏を取り、修正後はテストで検証、解決したら save_memory に保存」の注意が付く

費用の目安: 1 回の相談は入力 5〜15k トークン程度で、Claude Sonnet / Gemini Pro クラスなら数円〜十数円。
解決した内容は経験メモリに残るので、同じ問題は次回からローカルだけで解決できる。

## ブラウザ機能（v1.4.0）

LLM が **実際のブラウザ** で Web ページや自分で作った Web アプリを開いて確認できる（Playwright）。
「サーバーを起動しました」で終わらせず、コンソールのエラー・DOM の存在・見た目（スクリーンショット）まで
確かめてから完了報告する、という指示がシステムプロンプトに入っている。スクリーンショットはチャットに表示され、
vision 対応モデル（gemma3 / qwen2.5-vl / llava など）なら LLM にも画像として渡る。

導入（任意。入っていなければブラウザ系ツールは自動で隠れ、他の機能は今まで通り）:

```bash
.venv/bin/pip install playwright
.venv/bin/python -m playwright install chromium     # Playwright 同梱の Chromium を取得（約 150MB）
```

Linux で `playwright install` が依存ライブラリ不足を報告する場合は `.venv/bin/python -m playwright install-deps chromium`
（sudo が必要）。PC にインストール済みの Chrome / Edge / Firefox を使う場合は `browser.channel` を変えれば
`install chromium` は不要。

| ツール | 内容 |
|---|---|
| `browser_open` | URL を開き、ページのテキストとコンソールのエラー・JS 例外を返す |
| `browser_read` | 現在のページのテキストと、クリック・入力できる要素の一覧（番号付き） |
| `browser_click` / `browser_type` / `browser_press` / `browser_scroll` | 番号・表示テキスト・CSS セレクタで操作 |
| `browser_eval` | ページ内で JavaScript を実行（`document.querySelector('canvas') !== null` のような存在確認） |
| `browser_screenshot` | スクリーンショットを撮ってチャットに表示（クリックで拡大） |
| `browser_console` | コンソール出力（error / warning）と JS 例外 |
| `browser_close` | ブラウザを閉じる |

設定（`config.yaml` の `browser:`）:

| 項目 | 既定 | 内容 |
|---|---|---|
| `enabled` | true | false でブラウザ系ツールを LLM に見せない |
| `mode` | panel | **panel** は AperCode の画面内に表示（v1.7.0）。`headed` は別ウィンドウ、`headless` は非表示 |
| `channel` | chromium | `chromium`（Playwright 同梱）/ `chrome` / `msedge` / `firefox`（PC にインストール済みのブラウザを使う） |
| `cdp_url` | "" | 起動済みの Chrome に接続（`google-chrome --remote-debugging-port=9222` → `http://127.0.0.1:9222`）。ログイン済みのプロファイルをそのまま使える |
| `viewport` / `timeout` / `locale` | 1280x800 / 20 / ja-JP | 画面サイズ・待ち時間（秒）・言語 |
| `max_text_chars` | 6000 | ページのテキストを LLM に渡す最大文字数 |
| `external_sites` | ask | `localhost` 以外を開くときの確認（ask / allow / deny）。承認ダイアログで「常に許可」を選べば以後は確認しない |

### アプリ内ブラウザ（v1.7.0）

既定（`browser.mode: panel`）では、ブラウザは別ウィンドウではなく **AperCode の画面右側のパネル** に表示される。
画面右上の地球アイコン（または画面左の「ブラウザ」ボタン）でパネルを開閉し、上部の欄に URL を入れて Enter で開く。LLM が browser_* ツールを使い始めると
パネルが自動で開き、LLM の操作がそのまま映る。パネル上では次の操作ができる。

| 操作 | 内容 |
|---|---|
| クリック・ダブルクリック・右クリック・スクロール | そのままページに伝わる |
| 文字入力 | パネルをクリックしてから入力。日本語入力（IME）、Ctrl+V の貼り付け、Enter / Tab / 矢印キー / Ctrl+A なども可 |
| ◀ ▶ ⟳ | 戻る・進む・再読み込み |
| ✕ / ⏻ | ✕ はパネルを閉じるだけ（ブラウザは動いたまま。LLM は使い続けられる）、⏻ はブラウザを終了 |
| 幅の変更 | チャットとパネルの境界をドラッグ |

仕組みは、Playwright の Chromium を非表示で動かし、その画面（CDP の screencast）をパネルに配信している。
パネルの大きさに合わせてページの表示サイズが変わるので、LLM のスクリーンショットもパネルと同じ見た目になる。
パネルを閉じている間は配信を止める。別ウィンドウで表示したい場合は、設定画面の「ブラウザ表示」を `headed` にする。

ブラウザは 1 サーバーにつき 1 つを保持し、ツール呼び出しをまたいでページの状態（ログイン等）を引き継ぐ。
画面左の「ブラウザ」ボタン（v1.4.1）から URL を指定して自分で起動することもでき、LLM はそのページを引き継いで確認に使う
（ボタンの ● は起動中の印。ダイアログの「ブラウザを閉じる」で終了）。
`permissions.browser_*` は既定で `allow`（外部サイトだけ `browser.external_sites` で確認）。

## 補助ツール（v1.5.0）

LLM 自身が「あると作業が楽になる」と挙げたツールを追加した。いずれも追加の導入は不要（PDF だけ poppler か pypdf が要る）。

| ツール | 内容 |
|---|---|
| `repl` | 永続的な Python / Node の REPL。変数・import・関数定義を次の呼び出しに引き継ぐ（`run_command` は毎回新プロセス）。最後の式の値を `=>` で返す。Python はプロジェクトの `.venv` があればそれを使う。`reset: true` で再起動。`repl.timeout`（既定 60 秒）を超えると再起動して状態は失われる |
| `process_start` / `process_status` / `process_logs` / `process_stop` | サーバーなど長時間動くコマンドをバックグラウンドで起動し、ログをファイルに記録。`port` を渡すと待ち受け開始まで待つ（`process.wait` 秒）。停止は SIGTERM → 5 秒後 SIGKILL。AperCode 終了時にまとめて停止する |
| `read_document` | PDF（`pdftotext` または `pypdf`）/ Word / Excel / PowerPoint / OpenDocument / CSV をテキスト化。docx・pptx・xlsx はライブラリ無しでも読める（openpyxl があればそれを使う）。`pages` / `sheet` で範囲指定 |
| `check_js` | JavaScript / HTML の検査（下記） |

`repl` と `process_start` は `run_command` と同じく既定 `ask` で、「編集・実行を常に許可」の対象。危険なコマンドの検知（`rm -rf` など）は repl のコードにも効く。

### JavaScript / HTML の検査（`check_js`）

ローカル LLM は JavaScript の知識が弱く、ライブラリの呼び出し方を「記憶」で書いて動かないことが多い（初期化が何も生成しない、
CDN の URL が 404、など）。`check_js` はそれを実物で確かめるためのツール。

- **静的検査**（node があれば）: `.js` は `node --check` と `import` / `require` の解決（node_modules・相対パスの存在）。
  `.html` はインライン `<script>` を 1 つずつ構文チェックし、`<script src>` の相対パスが存在するか確認する。
  これは `write_file` / `edit_file` 直後の自動検証にも組み込んだ（`.html` も検証対象になった）
- **実行検査**（Playwright があれば）: ページを実際にブラウザで開き、JS 例外・`console.error`・失敗したリクエスト（404 など）を集める。
  `path` に HTML を渡すとそのディレクトリを一時的に配信して開く（`file://` では module / fetch が動かないため）。`url` で起動中のアプリも検査できる
- **probes**: 読み込み後に評価する JS 式のリスト。型・値・関数ならソースの冒頭を返す。
  `["typeof ForceGraph3D", "ForceGraph3D.toString()", "document.querySelector('canvas') !== null"]` のように、
  初期化の形（`Lib(el)` か `Lib()(el)` か）や要素の存在を確かめる
- **libraries**: CDN の URL だけを渡すと、空ページに読み込んで probes を評価する。実装前に API の形を確認するのに使う

システムプロンプトには「HTML/JS を書いたら完了前に check_js で開く」「ライブラリの初期化が不確かなら check_js(libraries=…) で
実物を見てから書く」を追加している。

## 変更前ファイルの自動バックアップ

エージェントが `write_file`（上書き）/ `edit_file` で既存ファイルを変更する直前に、元の内容を

```
<プロジェクト>/backup/<YYYYMMDD-HHMMSS>/<プロジェクト相対パス>
```

へ退避する。日時フォルダは「ユーザーの指示 1 回」につき 1 つで、その指示で変更された全ファイルの
変更前の状態がまとまる。ターン終了時に「変更前のファイル n 件を backup/... に退避しました」と表示される。

復元方法:
- チャットで「さっきの変更を元に戻して」と頼む → エージェントが `list_backups` で世代を確認し `restore_backup` で書き戻す
  （復元前の状態も新しい世代に退避されるので、やり直しも安全）
- 手動: `cp -r backup/20260920-153000/. .`（プロジェクト直下で実行）

`backup.keep_days`（既定 30 日）より古い世代は自動削除。`backup/` は list_dir / grep / glob の対象外。
`run_command` 経由の変更（`sed -i` など）は対象外なので、大きな変更の前は git commit も併用すること。

## Web 検索と知見の蓄積（行き詰まり対策）

エージェントは分からない問題に当たっても作業を止めず、次の順で解決を試みる（システムプロンプトに組み込み済み）:

1. エラー全文を読み、原因の仮説を立てる
2. `search_memory` で過去の経験を確認
3. `web_search`（DuckDuckGo → Bing → Brave → Mojeek の順に自動フォールバック、API キー不要。v1.2.1.1）で検索し、`fetch_url` で公式ドキュメント・GitHub Issue・Q&A を読む
4. 見つけた解決策を試す。効かなければ別のキーワードで 2〜3 回繰り返す
5. 効いた解決策は `save_memory` に出典 URL 付きで保存（次回は検索せずに済む）
6. それでも解決しない場合のみ、試したことを整理してユーザーに相談

ターン終了時の自動抽出（振り返り）でも、Web 由来の解決策は「（参考: URL）」付きで経験メモリに入る。

### 行き詰まりの自動検知（v1.1.6）

エージェント本体が次の状態を監視し、放置せずに介入する。

- 同じツール呼び出し（同じ引数）を 3 回以上繰り返した、またはツールの失敗が 3 回連続した（その間に検索していない）
  → 「同じ操作を繰り返さず、search_memory → web_search / fetch_url で解決策を調べてから別の方法を試すこと」という
  指示を履歴に差し込む（画面に「行き詰まりを検知…」と表示）。1 ターンに最大 3 回
- ファイルの変更・テスト・相談をせずに、調査系ツール（read_file / list_dir / grep / run_command など）だけを
  `stuck.no_progress_calls`（既定 12）回続けた（v1.2.6: 進捗なし検知）
  → 調査を止めて「立てた仮説と検証結果」「まだ確認していない層（表示・初期化・ライブラリの呼び出し方・環境）」「次に試す変更」を
  整理させ、クラウド相談が有効なら ask_cloud を促す。毎回違う調査をして堂々巡りするケースを拾う
- ツール呼び出し上限（`llm.max_iterations`、既定 60）に達した
  → 黙って止まらず、ツールを使わずに「完了したこと・未完了・問題と原因の推測・次の手順」の状況報告を生成する。
  「続けて」と送れば同じセッションで作業を再開できる

検索中は画面の状態表示が「Web 検索中」になる。DuckDuckGo がブロック（403）・結果なしの場合は Bing、Brave、Mojeek、さらに API キー不要の JSON API
（Stack Exchange、GitHub Issues、Wikipedia）を順に試し、
すべて失敗したときだけエラーになる（`web.engines` で順序を変更可）。それでも
検索がブロックされる環境では `config.yaml` の `web.provider: searxng` と `web.searxng_url` で
自前の SearXNG を使う。検索サイトの 403 は `ddgs` パッケージ（requirements.txt に含まれる。既存の venv では
`.venv/bin/pip install ddgs`）で回避できることが多い。入っていれば最初に使われる。`web.enabled: false` で完全に無効化。

`web_search` の `engine` 引数（v1.2.5）で検索先を指定できる: `mdn`（MDN Web Docs。JavaScript / DOM / Web API / CSS / HTTP の
公式リファレンス）、`stackexchange`、`github`、`wikipedia`、`duckduckgo`、`bing`、`brave`。システムプロンプトでは、
ブラウザ JS の仕様は記憶で書かず MDN を読んでから書くよう指示している（ローカルモデルは JS の細部を間違えやすいため）。

## 中規模プロジェクトを作るときのコツ

1. 最初に要件と設計を相談し、エージェントに `AGENT.md`（設計方針・構成・進捗）を書かせる
2. 機能単位で指示を出す。「全部作って」より「まず○○モジュールを作ってテストして」
3. 大きな調査や独立モジュールは子エージェントに任せるよう促す
4. セッションが長くなったら新しいセッションを作る。`AGENT.md` があれば引き継げる

## tool calling が使えないモデルの場合

tool calling 非対応モデル（`deepseek-coder-v2` など。選ぶと 400 エラーになる）を使う場合は、
`llm.tool_mode: json` にすると、モデルに次の形式でツール呼び出しを書かせて解析する:

````
```tool_call
{"name": "read_file", "arguments": {"path": "a.py"}}
```
````

## MT5 ツール

- `mt5_compile`: `.mq5` を `MetaEditor64.exe /compile` でコンパイル。MQL5 フォルダ外のファイルは `MQL5/Experts/AperCode/` にコピーしてからコンパイルし、`.ex5` を元の場所にも戻す
- `mt5_backtest`: `terminal64.exe /config:tester.ini` でストラテジーテスターを実行し、HTML レポートから純利益・PF・DD などを抽出

いずれも `WINEPREFIX=~/.wine_mt5` を使う（config.yaml で変更可）。

## Claude API を使う場合

```yaml
llm:
  provider: anthropic
anthropic:
  model: claude-sonnet-5-5
```

環境変数 `ANTHROPIC_API_KEY` を設定して起動。
